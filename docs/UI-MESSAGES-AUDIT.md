## 范围与计数说明

审查覆盖 VS Code 通知、侧栏状态、波形图、芯片信息、变量写入、外设寄存器、RTOS、CPU 负载、内存分析、SVD、CubeMX 固件提示及调试适配器错误出口。检查从底层错误到服务、消息、渲染器的传递过程，并核对触发条件、严重级别、占位符和操作结果。

清单扫描到 46 处直接通知调用，其中 Error 11 处、Warning 21 处、Information 14 处；中文和英文各 648 条文案。字典包含按钮、状态和成功提示，**648 不是报错数量**。Warning 调用也包含许可确认；同一句文案可能由多个入口展示。最终清单中的计数以其扫描快照为准。

错误内容还有三种动态来源：文件系统/网络异常、OpenOCD/GDB 原始输出，以及运行时插值。因此不能用一个固定数量穷举所有最终报错字符串。清单另列出 `src/` 中错误定义候选，它们包含内部和 Agent 错误，不能全部算作可见 UI 报错。

审计期间 `probeCoordinator.js`、`mainViewProvider.js` 和 CPU 采样相关文件出现了并行改动。未覆盖或撤销这些改动；本报告中的源码行号是扫描时的位置，测试结果对应执行时的工作区状态。CPU 部分的新改动不能视为已完成全面回归。

## 已确认的问题

### F1 · P2 · 部分失败、取消及未完成选择显示为“操作已完成”

位置：`src/mainViewProvider.js` 的 `executeCommand` 分发（扫描时约 4536 行），`src/services/svdManager.js` 的 `downloadOfficial` catch（约 356 行），`src/webview/sidebar/renderer.js:1841`。

分发器只把严格等于 `false` 的结果判为失败，其他返回值都发送 `commandSuccess`。SVD 下载失败时服务弹出真实错误、发送 SVD error 状态，但返回 `null`；随后侧栏底部被设成绿色“操作已完成”。用户取消 SVD/文件选择时也可能收到同样的完成反馈。SVD 卡片中的失败提示仍在，并非所有错误都消失，但两个 UI 出口相互矛盾。

实际复现：注入目录查询失败，先得到“SVD 下载/配置失败：AUDIT_NETWORK_FAILED”，再得到 `{ type: "commandSuccess" }` 和绿色完成状态。

ELF/探针/MCU QuickPick 的处理函数在展示选择器后即返回，保存和刷新发生于异步选择回调；通用完成提示早于选择完成，外层 catch 也无法捕获之后的全部回调错误。这一分支通过源码追踪确认。

建议：明确返回 `success/cancelled/failed`，成功提示只由真正完成的操作产生；文件选择 Promise 应等待确认或取消，并在选择回调中处理保存/刷新失败。

### F2 · P2 · ELF/DWARF 总体警告未显示，部分解析失败看起来像正常空列表

位置：`src/mainViewProvider.js` 的 `_sendElfSnapshot` / `_onElfChange`；`src/webview/sidebar/renderer.js:1868`、`:1897`；`src/webview/liveWatch/renderer.js:2479`。

宿主在 Reset/Done 消息中提供 `warnings`，但两侧渲染器均不消费该字段。侧栏只展示 `error/errorKey`，在已有符号的 DWARF 失败路径中 `error` 又被设为空字符串；波形的 Done 消息同样只带 warnings，渲染器只结束加载。因此缺少 DWARF、解析受限/失败等总体风险说明会丢失。符号自身的 `unsupportedReason` 仍可能展示，不能代替全部总体警告。

实际复现：执行生产 `_sendElfSnapshot`，携带唯一 warning 标记分别发给侧栏和波形，两者均未显示。

建议：提供独立可见的诊断区域，保留 warnings，并区分“读取成功但类型信息不完整”“未找到变量”和“解析失败”。

### F3 · P2 · RTOS 刷新错误不显眼，旧快照没有历史标记

位置：`src/webview/sidebar/rtos.js:64`、`:67`、`:168`、`:187`。

刷新错误仅设置刷新按钮的 `title`，任务表和可见状态中不展示错误。目标继续运行或停止代次改变后，旧快照仍参与正常渲染，且没有应用已有的 `rtos.stale` 文案。任务行内的 running/ready 等状态属于旧暂停快照，容易被理解为当前状态。调度器未启动、无任务等字典提示也没有接到明确的空状态展示。

实际复现：暂停快照展示 Worker；发送读取失败后错误只在按钮 title；发送继续运行和新 stopEpoch 后，Worker 仍在表中，RTOS 区域没有历史快照标记。

建议：增加可见且可访问的状态/错误行；按会话、停止代次及 inspectionEpoch 标记历史快照，明确说明暂停读取、无任务或部分结果。

### F4 · P2 · ELF 错误的路径、大小上限在 UI 中被丢弃

位置：`src/mainViewProvider.js` 的 `refreshVariables` catch（扫描时约 4687 行）及烧录后刷新 catch；`src/webview/sidebar/renderer.js:77`。

若异常具有 `i18nKey/i18nParams`，部分 liveError 发送点只传 key 和 message，没有传 params。渲染器优先使用 key 重新翻译，忽略已经插值完整的 message；缺失占位符会被替换为空。

实际复现：原始错误“ELF 超过 64 MiB 安全上限，已拒绝解析：firmware.elf”，刷新变量后的显示变成“ELF 超过  MiB 安全上限，已拒绝解析：”。读取失败路径也可能只剩“无法读取 ELF：”。

建议：统一转换异常为 UI 消息并完整携带 key、params、message 和 diagnostic；有 key 时先确认参数完整。

### F5 · P2 · GDB 端口占用误诊为 Tcl 端口占用

位置：`skills/_emberprobe/openocd-diagnostics.js:141`。

`address already in use / couldn't bind` 等绑定错误均产生 `TCL_PORT_IN_USE`，没有区分 GDB/Tcl/Telnet。调试模式同时开放 GDB 和 Tcl，因此此分支不只会接到 Tcl 错误。

实际复现：输入“couldn't bind gdb to socket on port 3333: Address already in use”，结果却为“OpenOCD Tcl 端口已被其他进程占用”，并建议更换 Tcl 端口。此建议无法解决 GDB 3333 端口冲突。

建议：解析日志中的服务与端口；不能确定时用通用 OpenOCD 端口绑定错误，避免指定错误的端口设置。

### F6 · P2 · OpenOCD 的执行权限/系统错误被隐藏为“未检测到”

位置：`src/openocdChecker.js:356`；`src/webview/sidebar/renderer.js:77`、`:1534`。

探测的 ENOENT、超时和不可识别输出有专用 errorKey，但 EACCES/EPERM 等非 ENOENT 异常通常只提供原始 message。状态解析仍赋予 `oc.missing` key；UI 优先显示 key，从而忽略实际执行错误。

实际复现：向生产状态解析器传入 `spawn audit.exe EACCES`，卡片显示“未检测到 OpenOCD”。存在但无执行权限的文件被表现成缺少安装，导致排查方向偏离。

建议：区分“文件不存在”“不可执行/访问被拒绝”和“探测失败”；没有专用 key 时展示原始 message 或带 error 占位符的探测失败文案。

## 文案改进建议

### N1 · P3 · 低电压提示没有保留 VTref 与测量能力的限定

`src/openocdRunner.js` 中原始事件为“参考电压异常……核对供电、VTref 接线与探针测量能力”，但 `run.voltageLow` 的中文和英文仅强调目标可能未供电。它使用“可能”，并未断言断电，因此这里不是确证的错误诊断；不过 UI 优先翻译 key 后丢失了更完整的排查条件。建议与底层诊断采用一致、保留测量不确定性的表述。

### N2 · P3 · 缺失驱动 helper 的报错错误声称它已签名

`src/services/probeDriverService.js:126` 为“The signed Windows driver helper is not installed”。[J-Link 兼容性说明](JLINK-COMPATIBILITY.md) 明确发布包的 helper/libwdi 未签名，哈希校验不认证发布者。另外同一个 catch 同时涵盖 helper 和 libwdi 缺失，不能准确判定只是 helper 未安装。

建议：改为“Windows driver helper or required libwdi library is missing or inaccessible”，删除 signed，并保留具体失败文件与原因。

## 已核对的合理行为

- 中文和英文键集合、占位符集合一致；本次未发现字典层面的中英文参数不对称。
- 烧录后的 ELF 刷新和恢复采样失败使用专门 warning，软件测试证明它们保持烧录成功结果。记录成功连接的服务也吸收保存失败，不能仅凭上层 await 推断会把烧录成功误报为失败。
- 常见 USB 断开、权限拒绝、占用、驱动不支持和目标无法建立 SWD/JTAG 连接具有独立诊断分支；未知打开失败没有直接断言驱动不兼容。
- 调试状态与写入结果区分可读、可写和快照就绪，失败写入有专门反馈；保留会话和代次检查。
- 低覆盖率 CPU 指标与静态内存占用说明在原扫描版本中保留了估算限制；软件审查不能证明实板测量准确度。

以上仅说明检查到的分支设计合理，不意味着所有未列问题的硬件故障都已验证。

| F1 | ELF、探针和 MCU 选择等待确认与保存后才报告成功；取消发送独立中性反馈，异步保存错误进入失败反馈。SVD 下载失败抛出错误，无匹配资源返回失败，取消返回取消；清除绑定仍算成功。CubeMX 选择、版本输入与固件流程同步区分成功、取消和失败。 |
| F2 | 侧栏变量区、波形面板及变量导入窗口显示 ELF/DWARF 总体诊断。宿主在类型解析结束时继续传递 warnings；解析失败有可见错误，切换 ELF 清理旧诊断，版本不匹配的结果被忽略。诊断按纯文本渲染、去重并限制条数和长度。 |
| F3 | RTOS 新增可见状态与错误行，显示读取中、调度器未启动、无任务和部分结果。旧任务表保留但标记为历史快照；会话、stopEpoch、inspectionEpoch 或目标执行状态变化后不把旧快照当当前数据，拒绝迟到响应。 |
| F4 | 异常统一转换为携带 key、params、message、diagnostic 的 UI 消息；ELF 路径和安全大小上限保留，相关服务状态也保留本地化参数。 |
| F5 | 绑定日志区分 GDB、Tcl、Telnet；无法识别服务时使用通用端口诊断。端口取自日志，未报告 GDB 端口时不误用已配置的 Tcl 端口。 |
| F6 | EACCES/EPERM 使用权限拒绝文案并保留路径和原始原因；其他探测错误显示具体失败原因，ENOENT 仍使用文件缺失提示。 |
| N1 | 中英文低参考电压提示都保留供电、VTref 接线及探针测量能力的限定。 |
| N2 | 删除 helper 已签名的错误声明；缺少或无法访问 helper/libwdi 时保留实际失败文件和原因。 |
