# 波形图历史长度性能审计

测量日期：2026-10-06。下文耗时、堆占用表来自扩容前的审计基线；随后历史保留策略已改为最近 30 分钟。

## 已实施的 30 分钟策略

- 未显式设置 `emberprobe.maxSamples` 时，按采样时间戳保留最近 1,800,000ms，兼容 0.1–200Hz 及采样中的频率切换。采样周期使用实际取整后的毫秒值；例如 181.9Hz 与 200Hz 均可能对应 5ms。
- 降频不会套用新频率的点数容量删除之前的高频历史；升频也无需重建缓存。时间边界最多有一个实际采样周期的离散误差，历史跨度不超过 30 分钟。
- 每通道有效点数硬上限为 360,001（30 分钟 × 200Hz，含两端）。显式配置点数上限仍可进一步缩小缓存，同时受 30 分钟时间上限约束。
- 过期对象即时释放，数组使用头部游标，每累计 4,096 个过期槽位集中整理一次；有效点数达到硬上限时，数组最多额外保留 4,095 个空槽位。避免高频采样逐点移动数十万个引用。
- 同一消息的采样时间会裁剪未更新通道，断续采样不会留下超过时间边界的旧通道历史。冻结快照、局部导出和绘图均只读取有效点；冻结视图保留独立快照，后台继续裁剪实时数据。
- 时间边界改为读取各通道首尾有效点，避免每帧为查边界扫描全部历史；采样率统计批量移除过期时间戳，避免大批消息逐个移动数组。

针对性验证覆盖全部 2,000 档频率的容量计算，0.1、30、181.9、200Hz 的 31 分钟模拟采样，重复升降频率、失效采样、无新样本通道、长时间间隙、冻结和导出。未进行全量检查或真实探针测试。

## 结论

30Hz、少量通道下，10 分钟是可以考虑的第一档目标。相较 3 分 20 秒，3 通道全历史重绘的中位耗时从约 2.8ms 增至 6–7ms，数据和绘图缓存的 V8 堆增量估算从 5.5MiB 增至 11.4MiB。仅显示最近 30 秒时，10 分钟历史的重绘约 3.1–4.5ms。

30 分钟、多通道或 200Hz 场景需要先优化数据结构及绘图准备阶段。10 通道、30Hz、30 分钟的全历史重绘中位耗时为 53–71ms，P95 为 89–104ms；3 通道、200Hz、10 分钟为 47–56ms，P95 为 60–75ms。这些同步操作会占用 Webview 主线程。

延长保留时间不会增加相同频率、相同通道集合下的目标 RAM 读取次数。额外成本主要发生在 Webview 的内存、历史扫描、临时对象分配、绘图准备和冻结复制；本审计没有测量真实探针吞吐或 Extension Host 的端到端延迟。

## 扩容前限制的来源（审计基线）

不存在固定的“3 分 20 秒”上限。时间覆盖约为 `(保留点数 - 1) × 实际采样周期`，还会受到分块裁剪影响。

- `emberprobe.maxSamples` 默认每通道 2,000 点。显式设置该选项会关闭自动保留点数调整。
- 未显式配置时，自动策略按实际周期保证至少 60 秒，并额外补偿最多 256 点的分块裁剪。
- Webview 配置和自动缓存存在每通道 20,000 点硬上限。
- 30Hz 的配置周期会取整为 33ms，实际按约 30.3Hz 计算。当前默认自动上限是 2,076 点，通常约保留 65–69 秒，而不是 200 秒。
- 200 秒可能来自 2,000 点 / 10Hz 或约 6,000 点 / 30Hz；当前截图没有数据，不能据此确定用户观察到的 200 秒属于哪种配置。
- 每通道 20,000 点在 33ms 周期下约覆盖 11 分钟，在 5ms 周期下约覆盖 100 秒。提高同一个点数配置不会为所有频率提供相同时间跨度。

代码依据：`src/liveWatchView.js` 配置归一化；`src/mainViewProvider.js` 的 `autoMaxSamples` 设置；`src/webview/liveWatch/renderer.js` 的 `retainedSampleLimit` 和 `onSamples`。

## 测量方法与边界

使用仓库真实的 `renderer.js`、`chart.js`、`chartInspection.js`、`analysisState.js`，生成普通浮点通道数据。运行机器为 Windows、AMD Ryzen 7 H 255 W/ Radeon 780M。

- 浏览器：Codex 内置 Chromium 154，Canvas 为 987 × 536 CSS 像素。执行两轮独立测量，第二轮在 Node 测量完成后运行。每个视口先预热 8 次，再记录 30 次重绘，报告两轮中位数范围及较高 P95。
- 每次重绘前主动使缓存失效，模拟收到新样本后的绘图准备路径。测量包含历史分段、时间边界、统计、几何构建、Canvas 命令和控件刷新。计时结束于同步 `draw()` 返回，不包含后续 GPU 完成、合成、消息传输和端到端帧呈现；不能直接换算成保证帧率。
- 内存：Node v24.13.1、V8，独立进程，JSDOM，显式 GC 后记录相对空 Webview 的堆增量。Canvas 被测试桩替代，所以这里没有浏览器 GPU/画布内存；也没有 VS Code、Extension Host 或 DOM 基线。它是相同数据结构的堆成本估算，并非 Chrome 整个进程的实际占用。
- 高于现有 20,000 点限制的场景，仅在基准中预填数据并覆盖运行时点数，用于评估候选容量。生产配置和裁剪逻辑保持原样。
- 数据不含 64 位整数文本、断线间隙或复杂运行时对象。长 `valueText`、BigInt 精确整数偏移、归一化、采样率切换等可能产生额外开销。

## 开销为何随历史长度增长

1. `onSamples` 对每通道写入 `{t, v, valueText}` 对象；裁剪通过 `splice(0, remove)` 分块移动数组。平均写入成本较小，但容量增长会放大偶发裁剪和 GC。
2. 新样本调用 `invalidateSeries()`；`chartData()` 遍历完整保留历史并重新构建分段数组，`retainedTimeBounds()` 也扫描完整历史。因此只显示最近 30 秒仍受到总历史长度影响。
3. `chart.js` 在准备统计时扫描各分段。几何构建已通过二分查找裁剪到视口，因此短视口比显示全部便宜；全历史视口依然创建每个原始点的几何对象。
4. `envelope()` 保留每像素列的首尾和极值，限制最终绘制线段数量，却没有限制统计扫描和原始几何对象数量。3 通道从 200 秒到 1,800 秒时，总几何点从 18,186 增至 163,641，但绘制点只从 5,590 增至 6,708；主要增长来自绘图前的工作。
5. `Analysis.freeze()` 复制所有保留点。隐藏通道也保留采样数据；不能仅用当前看见的曲线数估算所有存储和冻结开销。
6. 内存历史的 CSV 构建会额外分配结果字符串；本次未测量 CSV 峰值。扩展已有独立磁盘采样归档，增加 Webview 保留时间不是保存更长会话数据的唯一途径。

## 建议的后续实现顺序

先将低频、少量通道的目标设置为按时间计算的 10 分钟。30Hz 下约需 18,183 点，补偿裁剪后约 18,440 点，尚在当前 20,000 点上限内；这不意味着 200Hz 的 10 分钟也适合直接启用。

扩到 30 分钟或支持多通道高频长历史前，建议依次处理：

1. 用环形缓冲区替代前端 `splice`，减少裁剪尖峰；明确所有直接数组访问的契约。
2. 增量维护时间边界、分段信息和统计，先裁剪视口，再做准备工作，减少每次样本触发的全量遍历。
3. 对长历史建立多级极值摘要；全景图绘制只读取匹配像素分辨率的层级，同时保留原始精度用于短视口、悬停和导出。
4. 以所有通道的总点数/内存预算控制容量，冻结快照和多个图表面板也计入预算。高频长会话可借助磁盘归档与按需加载。
5. 若最终提高上限，需同步调整配置归一化、自动时间计算、裁剪截止时间、20,000 硬限制、冻结复制限制，并验证采样率切换；只改其中一个常量会造成行为不一致。

本次未启用上述策略，仅交付性能测量和建议。

## 复现

```powershell
node --expose-gc test/perf/chart-history-bench.js
node mockup/build.js
node test/perf/chart-history-bench.js --browser-html
```

在正在运行的本地预览服务中打开 `http://localhost:8085/history-bench.html`；完成后页面显示 JSON。Node 结果写入 `output/performance/chart-history-node.json`。此次浏览器两轮结果保存为 `chart-history-browser.json` 和 `chart-history-browser-repeat.json`，位于同一目录。

基准是手动运行的审计工具，没有注册到常规测试套件。本次仅运行基准、该脚本的 ESLint/Prettier、构建及 diff 检查，没有运行全量检查或真实硬件测试。
