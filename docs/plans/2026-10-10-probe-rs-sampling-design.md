# probe-rs 采样频率优化

目标：修正用户报告的设定 20 Hz、单变量实际约 13 Hz，并减少多变量 LiveWatch 的 DAP 请求次数。后续 J-Link / F407_car 真机反馈为 6.4 Hz 且提高设定频率无效；通过现有 Agent Bridge 确认设定已为 100 Hz，实际约 6.43 Hz、读取耗时 P95 为 156 ms。保留所选会话、探针独占、ELF RAM 校验和写入事务。

## 原因与方案

- `DebugSessionBridge._poll()` 在每轮读取完成后等待完整周期，实际周期等于读取耗时加设定周期。以读取 25 ms、设定 50 ms 为例，旧行为约为 13.3 Hz。
- 现有 20 ms 最小间隔将 probe-rs 软件调度限制为最多 50 Hz，而频率设置允许 200 Hz。
- 读取计划只合并相邻和重叠变量，少量 RAM 间隙会增加 DAP 往返次数。
- Extension Host 验证发现 Windows 的普通定时器约 15.6 ms 粒度也会降低实际频率；运行期采样复用已有 `windowsTimerResolution`，停止、暂停、会话变化、空计划和重试耗尽时释放。原生定时器不可用时继续使用普通定时器，不在 Extension Host 中忙等待。
- probe-rs 0.32 的 [DAP 请求循环](https://github.com/probe-rs/probe-rs/blob/v0.32.0/probe-rs-tools/src/bin/probe-rs/cmd/dap_server/server/debugger.rs) 在运行且无请求时可能休眠 50 ms；软件调度优化不保证实板达到 200 Hz。

采用周期扣除读取及分发耗时，并在当前 ELF 可写分配区间内合并至多 64 字节的间隙；单次请求和每轮读取仍至多 4096 字节。不能合并的区间分组发送，每组最多 4 个请求，收完一组再检查会话状态并发送下一组；不预读下一轮。失败也等待本组全部请求完成，避免写入或控制与遗留读取交错。

真机反馈说明仅修正扩展调度不足。当前波形变量与写入卡片变量相隔 324 字节，分组发送可减少逐项等待；要消除每轮起始的上游空闲休眠，提供固定 probe-rs 0.32 源码的可唤醒构建。仅对 stdio 输入和空闲等待添加 Tokio 通知，不另建采样连接，不改变核心状态、读写或烧录实现。源码归档校验 SHA-256，构建在运行原生通知测试后输出独立程序，不替换已安装后端，不自动重启调试或访问硬件。

首轮授权真机复测中，仅增加通知的后端已将 20 Hz 设置提升到约 19.9 Hz，但 100/200 Hz 设置仍约 28.5 Hz、每轮读取 P95 约 35 ms。上游会为休眠核心的 `readMemory` 临时停核，状态等待含 1 ms 休眠；Windows 定时器精度按进程生效，后端不能继承 Extension Host 的精度申请。性能构建为 stdio 会话增加独立的 `timeBeginPeriod(1)` RAII 守卫，只有申请成功才在退出时匹配释放；其他平台无操作。保持核心状态及读写逻辑，另测实际改善。

第二轮后端精细定时器真机复测中，20 Hz 仍约 19.9 Hz，100/200 Hz 仍约 28.5 Hz，没有显著改善。进一步检查发现上游 J-Link 每次 USB 读写通过 `InterfaceExt` 创建和销毁端点；其 `usb_util` 已提供适合高频路径的持久端点辅助函数。后端改为在连接初始化时打开两个端点，并在原串行读写函数中复用，保留原辅助函数的超时取消、响应收尾、短写检查及整包读取兼容处理。连接和端点仍由同一 J-Link 对象持有，保留注销及释放顺序。

## 实施与验证

1. 新增无硬件回归测试，复现 20 Hz 与 25 ms 读取耗时的情况，覆盖 200 Hz、慢读取无重叠、重试、停止和状态变化。
2. 修改 `debugSessionBridge.js` 的运行期调度与读取合并；从 `mainViewProvider.js` 返回已验证的 RAM 区间供读取计划使用。未经验证的间隙、跨区间、过大间隙均保持独立读取。
3. 增加 Extension Host 回归，验证实际 probe-rs stdio 适配器上的高频采样、停止和清理；软件模拟结果不作为实板频率承诺。
4. 更新 probe-rs 使用文档与双语 Unreleased 记录，执行 `npm run check`、`npm run quality`、`npm run bundle`、`npm run test:e2e` 和 diff 检查。
5. 使用当前 MSVC/Rust 工具链构建可唤醒后端，运行请求先于等待到达、等待被请求打断和空闲轮询期限的原生测试。新后端真机测量单独记录，并在重新建立调试会话前取得所需授权。

## 软件测量

2026-10-10，Windows x64、Node 24.13.1、VS Code 1.136.1 Extension Host：模拟 DAP 读取延迟 25 ms，设定 20 Hz，采样约 19.9 Hz。仅修正周期但未启用精细定时器时，同一 IPC 测试约 16.9 Hz；原 25 ms 读取加 50 ms 等待在确定性时钟测试中约 13.3 Hz。1 ms 模拟读取可按 5 ms 周期采样，证明调度不再人为限制为 50 Hz；这不是探针实测。

## 真机结果

2026-10-11，J-Link / F407_car，经用户明确授权切换性能后端并重新建立采样连接。最终测得 20 Hz 设置约 19.88 Hz，100 Hz 约 29.17 Hz，200 Hz 约 29.16 Hz；每轮读取 P95 由 155 ms 降至约 34 ms。测试复用原监视变量，结束后恢复 100 Hz，并保留性能后端继续采样。高频仍受读取耗时限制；新增扩展请求分组由软件/Extension Host 验证，不计入本次使用已有扩展安装的真机结论。

## 撤回后端构建

2026-10-11，考虑到长期维护修改版 probe-rs 的成本，撤回后端构建脚本、对应测试和性能实测文档，EmberProbe 回到使用用户安装的原版 probe-rs。扩展侧的周期计算、RAM 间隙合并、4 请求分组和 Windows 定时器保留。原版 probe-rs 的频率限制见 [probe-rs 使用说明](../PROBE-RS-EMBASSY.md#原版-probe-rs-的频率上限)。
