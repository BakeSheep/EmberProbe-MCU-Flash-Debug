# H750_RttTest 真机调试启动耗时审计（2026-11-11）

## 实测环境与口径

- Windows，VS Code 1.145.2，STM32 配置档，已安装 EmberProbe 0.9.2。工作区 `H750_RttTest`，使用侧边栏原先选择的 `build/Debug/H750_RttTest-nosym.elf`，没有重新构建。
- STM32H750、CMSIS-DAP、SWD、`stm32h7x.cfg`。通过 VS Code F5 启动托管 `launch`，运行到 `main`，每轮结束后停止会话。临时配置开启 `performanceTrace`。
- 总耗时取 `entryStop.sinceStartMs`，从扩展处理调试配置到入口断点。`startup.openocd` 包括并行的 SVD 路径解析与 OpenOCD 路径解析。UI 轮询也观测到了入口断点，采样间隔与界面刷新使其读数略高。
- “首次”指审计开始后的第一轮，VS Code 在此之前已运行。没有执行 Windows 重启、重新插拔探针或清除系统缓存。

## 窗口重载后的额外等待

两次重载后约 11 秒按 F5，从按键到控制台首次显示入口事件分别为 62.413 秒和 62.411 秒。扩展内部计时分别为 32.029 秒和 32.569 秒。更早的一次试验在重载后约 1.4 秒按 F5，未观察到调试会话或入口事件，未纳入耗时表。

第二次同时采集了进程创建时间。按键工具调用返回耗时 58 ms，单次 UI 查询最长 120 ms。VS Code 日志在 F5 后 29.545 秒才记录内置 `vscode.debug-server-ready` 的 `onDebugResolve` 激活。OpenOCD 和正式 GDB 进程分别在 F5 后 54.645 秒和 54.949 秒创建。GDB 创建至入口事件的界面观测约 7.462 秒，接近适配器记录的 7.202 秒。额外约 30 秒位于 F5 到调试配置处理之间。日志未细分 VS Code 在调试解析前的等待，当前证据无法定位到具体扩展或任务。

另一次重载后 11.136 秒点击 EmberProbe 侧边栏的“复位调试”。点击后 31.221 秒看到活动会话，38.527 秒在调试控制台看到 `Temporary breakpoint 1, main ()`。这个入口没有开启阶段日志，这次的界面总耗时低于两次 F5 冷启动。

## SVD 扫描的独立复测

同一个扩展宿主中的 STM32Cube Core 初始化时设置了 `CMSIS_PACK_ROOT`，日志指向 `%LOCALAPPDATA%\stm32cube\packs`。该项目最初无 SVD 绑定。本地 EmberProbe SVD 库同时有 `STM32H750VBTx` 和 `STM32H750xx` 两个匹配项，项目目录下没有 SVD，自动发现继续进入包目录。

用 Node.js 24.13.1 运行仓库中的 `SvdManager`，使用已安装 0.9.2 的 SVD Worker、真实工程和相同的 SVD 库。调用只读取文件，绑定和导入通过测试替身拦截。两轮各用新的实例。

| 环境                                | SVD 路径解析 | 读取的 SVD | 校验调用累计 |
| ----------------------------------- | -----------: | ---------: | -----------: |
| 子进程内清空 `CMSIS_PACK_ROOT`      |       700 ms |          3 |       675 ms |
| 子进程内设置为 STM32Cube 实际包目录 |    27,988 ms |         93 |    27,664 ms |

包目录的 90 个候选中，88 个最终报 `SVD_DEVICE_MISMATCH`，另有两个匹配，自动发现最终仍未绑定。所有文件读取累计只有 294 ms。源码在判断芯片型号前对每个候选执行完整 XML 校验和解析，串行等待 Worker 返回，且失败会从校验缓存移除。这与重复 F5 都承担整段等待的观测一致。见 [托管启动](../../../src/services/debugLaunch.js)、[SVD 自动发现](../../../src/services/svdManager.js)及 [SVD 校验](../../../src/services/svdLibraryService.js)。

对照组只改变绑定状态时，解析阶段从 22,209–22,391 ms 降到 4 ms。绑定后用默认 OpenOCD 路径复测也是 5 ms。这个结果把当前项目的主要瓶颈定位到调试启动关键路径上的 SVD 自动发现。下载、探针和 GDB 阶段的耗时在对照中基本保持同一量级。
