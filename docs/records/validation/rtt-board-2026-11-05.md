# RTT board validation — 2026-11-05

Validation of the `feat/rtt-logging` extension flow and Agent paths on a real board, using the
`--suite rtt` runner (`test/hil/rtt-smoke.test.js`) in an isolated VS Code Extension Host.

## Setup

- Windows x64, OS build 10.0.26300; isolated VS Code 1.136.1 Extension Host.
- STM32H750 with CMSIS-DAP_JX (c251:f001, serial 0001A0000000, HID); xPack OpenOCD 0.12.0-7, `stm32h7x.cfg`, SWD.
- Firmware `STM32Project/H750_RttTest`, presets Debug (control block in DTCM, 0x200041a4), AxiCached and AxiNoncached
  (AXI SRAM, 0x24004040), each with a `-nosym.elf` for the scan fallbacks.
- The results below used firmware whose `mode` command was unusable on channel 1 (see Findings), so those runs set the
  mode by writing `_SEGGER_RTT.aUp[1].Flags` through the Agent `variables.write` route.

## Findings

1. **Probe wedge, not caused by RTT.** The probe stopped answering three times in the suite, each time while firmware
   was being downloaded. It reproduces with no extension, session or RTT: a loop of plain OpenOCD running the Agent
   flash command wedged on run 5 at 10 MHz and on run 1 at 1800 kHz, both in the Flash programming step, so the raised
   clock is not the cause. OpenOCD then fails `CMD_INFO` with `hid_write ... 0x3E5` at any clock, the probe did not
   recover in 10 minutes, and a replug clears it. Another CMSIS-DAP with the same `FW 1.0` wedged the same way on
   2026-10-20, which points at the probe, but other probes and `cmsis-dap quirk` were not tried.
2. **Search stall at 1800–2000 kHz.** On this probe, `rtt start` over a large range gives
   `CMSIS-DAP command mismatch` and a stall of about 6 s; 500, 1000, 3000, 4000 and 8000 kHz are fine, and 1800 kHz is
   the `stm32h7x.cfg` default. The stall exceeds the 5 s RPC timeout and reset the session under a misleading message.
   It now reports `RTT_SCAN_TIMEOUT`. Setting `samplingAdapterSpeedKhz` to 4000 passes. One earlier run passed the
   section scan at the default clock under a live-watch session; that was not explained.
3. **Firmware `mode` command.** `SEGGER_RTT_ConfigUpBuffer(channel, NULL, NULL, 0u, mode)` replaces the buffer of a
   channel above 0 with an empty one, so channel 1 vanishes and block mode hangs the main loop. This is a firmware bug,
   not an EmberProbe one. It now calls `SEGGER_RTT_SetFlagsUpBuffer`. With the rebuilt AxiNoncached firmware, `mode.trim`
   and `mode.block` pass through the firmware command, and the suite now depends on this fix.
4. **Error classification.** The `error writing` rule in `skills/_emberprobe/openocd-diagnostics.js` also matches
   `error writing data: hid_write`, so a wedged probe is reported as `FLASH_WRITE_FAILED` even on read-only operations.
5. **MCP operation label.** `src/mcp/server.js` labels every failure with `tool.methods.at(-1)`, so a failed
   `rtt_control` start reads `rtt.stop`.
