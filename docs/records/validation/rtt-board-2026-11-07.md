# RTT feature board validation — 2026-11-07

Board checks of the RTT features that `rtt-board-2026-11-06.md` left unverified. This validation is unfinished: the first
complete run with the new steps failed from `follow.debugFromSampling` onward, and it was stopped before it ended.

## Setup

- Windows x64 with an isolated VS Code 1.136.1 Extension Host.
- STM32H750 with J-Link V9, serial 20781318, SWD at 4 MHz, using the bundled OpenOCD (the `master` build).
- Firmware `STM32Project/H750_RttTest`, preset Debug, control block in DTCM at 0x200041c8.
- The firmware gained the `enc <name>`, `vterm` and `rx` commands, and down channel 1 now also answers on channel 0.
- Suite `test/hil/rtt-smoke.test.js`, with the new steps listed below.

## Verified

Input, channels, formats, encodings, virtual terminals and raw logs passed in the complete run:

| Step                      | Verified behaviour                                                                                      |
| ------------------------- | ------------------------------------------------------------------------------------------------------- |
| `input.lineEndings`       | The firmware received exactly `lf`, `crlf`, `cr` and `none` endings                                     |
| `input.raw`               | `ab`, 0x03, 0x7F and U+4E2D arrived as typed, UTF-8 encoded, with no local echo                         |
| `channels.downMapped`     | Crossed mapping: terminal 0 reached down 1 and terminal 1 reached down 0                                |
| `channels.downInputOnly`  | With up 1 unread and 8000 B/s on it, input reached down 1 and the firmware dropped 0 bytes over 4 s     |
| `format.hex`              | Channel 1 showed offset, hex bytes and ASCII rows                                                       |
| `format.raw`              | ANSI, LF, CRLF and CR reached the terminal unchanged                                                    |
| `encoding.channelDefault` | gbk, gb18030, big5, shift_jis, euc-kr and latin1 decoded a sample cut across reads                      |
| `encoding.perChannel`     | A per-channel override applied to the terminal, log and Agent read; input stayed UTF-8                  |
| `vterm.switch`            | `[T1]`, `[TA]`, `[T2]` and `[T3]` prefixes, an interrupted line, and a switch cut between its two bytes |
| `vterm.off`               | With the setting off and latin1, the switch bytes stayed as text                                        |
| `log.raw`                 | `rtt.bin` for one channel and `rtt-chN.bin` for several kept GBK and ANSI bytes unchanged               |

The older steps through `follow.sampling` also passed in this run, including the 96000 B/s stress steps.

`autoStart` passed only in the run of new steps: it stayed stopped with no session, followed sampling and debug, and
stayed stopped after a manual stop.

`autoStart.modeRefused` is weak. It passed in both runs, but it only checks that RTT stays stopped, because the refusal
does not appear in `rtt.status`. The message itself was not checked.

## Open failure

`follow.debugFromSampling` and `follow.debug` failed with `RTT_START_TIMEOUT`: "RTT gave up after 12 attempts: no control
block found in the searched memory". After that, a debug session held the probe, so `follow.flash` and
`autoStart.noSession` reported `PROBE_BUSY`, and later steps reported `RTT_NOT_RUNNING` or the same timeout. Those later
failures, including `autoStart.*`, `skill.path`, `mcp.path` and `locate.*`, are not evidence about those features yet.

The cause is unknown. Both `follow` steps passed on 2026-11-06, in a run without stress steps. This was the first run to
execute the stress steps before them, and `autoStart.debug` attached without trouble in the run without stress. Those
facts point at state left by the earlier steps, but this has not been tested and a product fault is not ruled out.
