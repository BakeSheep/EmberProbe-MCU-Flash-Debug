# RTT feature board validation — 2026-11-10

Follow-up to `rtt-board-2026-11-07.md`, whose complete run failed from `follow.debugFromSampling` onward. The complete
suite now runs through on the Debug preset with one intermittent failure, `firmware.softReset`, whose cause is in
OpenOCD and is not fixed yet.

## Setup

- Windows x64 with an isolated VS Code 1.136.1 Extension Host.
- STM32H750 with J-Link V9, serial 20781318, SWD at 4 MHz, using the bundled OpenOCD (the `master` build).
- Firmware `STM32Project/H750_RttTest`, preset Debug, control block in DTCM at 0x200041c8.
- Suite `test/hil/rtt-smoke.test.js` with stress steps enabled, RTT polling at 10 ms.

## Changes under test

- A start on a debug server waits as long as an automatic start (about five minutes for an exact control block). A
  debug launch stops at its entry point after the startup code cleared the block, so twelve attempts were too few.
- A data port that keeps refusing connections makes the controller re-attach once; a channel that still cannot connect
  ends the run with `RTT_CHANNEL_DISCONNECTED` instead of staying `running` with no data.
- A start that cannot get a session leaves a pending controller as it was, so its wait still ends in a resume.
- A download that cannot reserve the probe is refused before RTT or live watch is interrupted.
- The suite continues the target past the debug entry stop, and `autoStart.debug` continues a paused target before it
  stops debugging. Stopping a paused debug session leaves the target halted; the product still does that, only the
  suite works around it.

## Open failure: output stops after a soft reset

In the second complete run the firmware acknowledged `reset`, and no output arrived for 15 s afterwards. The status
saved at the failure showed:

- RTT `running` on the own session, both channels connected, generation unchanged since `follow.flash`.
- Channel 0 on the host had received 510 bytes, all from before the reset.
- The target's channel 0 held 779 bytes with read offset 0: the banner and heartbeats were written and never read.

OpenOCD's RTT poll (`read_channel_callback` in `src/rtt/rtt.c`) unregisters itself and stops RTT after any failed
read, while the TCP servers stay open. A poll that lands while the core is in reset fails, so RTT stops for good with
nothing for the extension to notice. With polling at 10 ms the poll only sometimes meets the reset window, which
matches 1 failure in 10 soft resets across these runs. The mechanism comes from the source and the saved telemetry; a
failing poll was not observed directly, because the OpenOCD log of that run was not kept.

The connection-loss re-attach above does not cover this, because the data ports stay connected. The planned stall
watchdog does: target buffers that hold data while the host receives nothing for several seconds trigger one
re-attach. Until then a reset of the target, by command, button or watchdog, can silently stop RTT output.

## Stall watchdog

Later the same day the controller gained the stall watchdog: when a channel's target buffer holds data, and neither its
read offset nor the host byte count moves over three telemetry samples and at least 3 s, RTT gets one `rtt stop` and a
full start on the same session. The new step `firmware.resetRepeat` sends `reset` repeatedly in one RTT session and
expects the banner and a heartbeat after each. These runs skipped `flash`; the board already held the same Debug
firmware.

| Run               | Resets           | Result                                                                                |
| ----------------- | ---------------- | ------------------------------------------------------------------------------------- |
| First, 30 resets  | ended after 43 s | Stall detected and RTT restarted on the own session; the step failed on a test defect |
| Second, 30 resets | 30               | All 30 banners seen; one stall, after reset 22, restarted and resumed; 51 s           |

In the first run the suite's read helper treated the brief `starting` state of the restart as a failure, so the step
ended there. The status saved at that point showed RTT running again on the own session, generation 2, both channels
connected, with `recovery` naming channel 0. Whether output resumed in that run was not checked. The helper now waits
through `starting`, and the second run passed. Both runs stalled once, in line with the earlier 1 in 10 soft resets;
the samples are too small for a rate.

## Complete run with the watchdog

The complete suite with stress steps, including `flash` and 20 resets in `firmware.resetRepeat`, passed 64 of 64 steps.
`firmware.resetRepeat` reported no restart. `firmware.softReset` took 6.6 s against 1.8 to 2.7 s in the earlier runs,
which fits one restart, but the step did not record the status and the run's logs were not kept, so this is not
established. The step now returns the status's `recovery`.
